## 6. Core Architecture Summary

The pilot extends a standard AI interaction.

A generic AI interface usually follows this pattern:

```txt
user input
→ model response
```

AI JOKER-C2 extends the process into a governed runtime chain:

```txt
user input
→ IPR identity binding
→ governance classification
→ policy / risk / oversight evaluation
→ OpenAI cognitive engine
→ model output
→ governed EVT trace
→ EVT/IPR-bound memory event
→ OPC proof receipt
→ engineHash
→ opcChainHash
→ verification metadata
→ auditable response package
```

The result is not only an AI answer.

The result is an AI answer connected to operational identity, event traceability, memory continuity, proof receipt and audit metadata.

## 10. Privacy and Security Boundary

Recommended review posture:

```txt
Synthetic data first.
Public data where appropriate.
No secrets in prompts.
No production credentials in chat.
No sensitive identity documents in the demo runtime.
Hash-oriented proof where possible.
GDPR-minimized metadata.
Fail-closed behavior for unsupported or unsafe contexts.
```

The OpenAI API key must be configured only in deployment environment variables or another secure secret store.

It must never be committed to the repository, logs, screenshots, README files, public documentation or chat messages.

## 11. Current Limitation Summary

The pilot is validated as a working demo, but it is not yet a production-grade regulated service.

Known limitations:

- prototype ledgers still require persistent external storage for production use;
- local/serverless JSONL storage is not sufficient for long-term evidence retention;
- OPC proof receipts are technical and not legally certified;
- proof verification endpoints can be expanded;
- signed proof receipts can be added;
- audit export can be strengthened;
- access control and retention policies require production hardening;
- future migration to Responses API should preserve the same HBCE proof chain.
