SaaS Core v0.1 is the first operational SaaS definition of AI JOKER-C2.

It defines the minimum governed runtime required to transfer JOKER-C2 from an HBCE R&D prototype into a demonstrable SaaS service based on verified IPR access, IPR-bound memory, model escalation, EVT continuity, OPC technical proof receipts, dashboard audit visibility, SaaS tier policy and a restricted C2 Defense boundary for authorized defensive cyber use.

## 2. Product thesis

SaaS Core v0.1 is not a generic AI chat product.

It is a governed AI runtime where each relevant interaction is evaluated through identity, context, risk, tier, model level, memory, event continuity and proof requirements.

Canonical product formula:

```text
AI governed through IPR.
Responses traced through EVT.
Proof receipts generated through OPC.
Runtime organized by MATRIX.
Execution delivered through JOKER-C2.

Commercial formula:

From prompt to proof.
From response to responsibility.

Operational formula:

IPR → runtime → tier → risk → model → response → memory → EVT → OPC → dashboard

3. SaaS Core v0.1 objective

The objective of SaaS Core v0.1 is to demonstrate that JOKER-C2 can operate as a governed SaaS runtime.

The release must prove the following:

A verified IPR subject can access JOKER-C2.
The runtime can distinguish generic access from IPR-verified access.
The runtime can evaluate a SaaS tier.
The runtime can select a model level according to policy.
The runtime can maintain IPR-bound memory or declare its memory boundary.
The runtime can generate EVT records.
The runtime can generate OPC technical proof receipts.
The dashboard can expose runtime state, identity state, tier, model, memory, EVT, OPC and risk.
C2 Defense remains restricted to authorized defensive cyber use.

SaaS Core v0.1 is considered successful only if the runtime can be demonstrated end-to-end through a repeatable HBCE self-pilot flow.

6. IPR Access Layer

The IPR Access Layer is the entry condition for governed access.

JOKER-C2 must not recognize a subject only because the user writes a name in the prompt.

The subject must be recognized through server-side runtime state.

Minimum IPR access states:

NOT_VERIFIED
CLIENT_TRANSPORT_ONLY
SERVER_VALIDATION_REQUIRED
IPR_VERIFIED_BIOLOGICAL_SUBJECT
IPR_VERIFIED_ORGANIZATION
IPR_VERIFIED_WORKSPACE

Minimum visible fields:

Runtime entity
Runtime IPR
Human IPR
Certificate ID
Certificate status
Access decision
Identity binding
Handoff source
Handoff authority
MATRIX state

Required behavior:

If no valid IPR handoff exists, runtime remains limited.
If handoff exists only client-side, server-side validation is required.
If server-side validation succeeds, IPR-bound access is granted.
If validation fails, runtime fails closed or remains limited.

Canonical statement:

JOKER-C2 does not identify the user from prompt text.
JOKER-C2 identifies the user through verified IPR runtime state.

7. SaaS Tier Policy

SaaS Core v0.1 must introduce tier-aware runtime behavior.

Planned SaaS tiers:

BASE
IPR
PRO
GOVERNANCE
C2_DEFENSE
STRATEGIC

BASE

BASE is for exploratory or non-verified users.

Access: limited
Memory: runtime only
Model: standard
EVT: optional or minimal
OPC: disabled or minimal
C2: unavailable

IPR

IPR is for verified individual subjects.

Access: verified individual
Memory: IPR-bound
Model: standard or enhanced
EVT: enabled
OPC: optional or enabled
C2: unavailable unless separately authorized

PRO

PRO is for professionals and structured workflows.

Access: verified IPR
Memory: IPR-bound
Model: enhanced or advanced
EVT: required for operational responses
OPC: enabled
Documents: enabled under policy
C2: unavailable unless separately authorized

GOVERNANCE

GOVERNANCE is for organizations, companies, teams and institutional workflows.

Access: verified organization or workspace
Memory: IPR-bound and workspace-bound
Model: advanced
EVT: required
OPC: required
Dashboard: required
Audit: required
C2: unavailable unless separately authorized

C2_DEFENSE

C2_DEFENSE is for authorized defensive cyber use.

Access: verified IPR + verified organization + authorized perimeter
Memory: IPR-bound and workspace-bound
Model: C2 escalated
EVT: mandatory
OPC: mandatory
Audit: mandatory
Policy: fail-closed
Use: defensive only

STRATEGIC

STRATEGIC is for B2B, B2G, critical infrastructure, pilot or contractual use.

Access: contractual or pilot
Memory: dedicated scope
Model: advanced or C2 according to agreement
EVT: mandatory
OPC: mandatory
Audit: mandatory
Dashboard: dedicated
Governance: dedicated

Canonical pricing principle:

The cost grows with the operational value of the response,
not only with the number of tokens consumed.

C2 Defense is a restricted defensive cyber perimeter.

It is not a public premium plan.

Access requirements:

verified IPR

authorized perimeter
defensive purpose
logging enabled
mandatory EVT

fail-closed policy

Allowed C2 Defense use cases:

defensive hardening
incident response support
authorized risk assessment
SOC documentation
configuration review
defensive vulnerability triage on owned or authorized assets
cyber governance planning
security posture review

Disallowed use cases:

unauthorized exploitation
credential theft
malware development or operation
evasion guidance
targeting third-party systems
offensive automation
harmful cyber instructions
unauthorized access guidance

Required behavior:

If authorization is missing, fail closed.
If perimeter is unclear, fail closed.
If request appears offensive, block.

Canonical statement:

C2 is not a premium subscription.

18. Runtime execution chain

The canonical runtime execution chain is:

1. Receive request.
2. Resolve IPR session server-side.
3. Resolve SaaS tier.
4. Classify context.
5. Evaluate risk.
6. Check C2 Defense boundary if cyber-relevant.
7. Select model level.
8. Generate governed response.
9. Update memory if allowed.
10. Generate EVT when required.
11. Generate OPC when required.
12. Return response with runtime metadata.
13. Update dashboard state.

If any critical authorization, perimeter or policy state cannot be resolved, the runtime must fail closed.
